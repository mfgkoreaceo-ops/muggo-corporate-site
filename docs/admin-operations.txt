상태: 사용자 승인에 따라 GitHub Pages 정적 배포 대상으로 준비한 변경입니다. 인증 서버는 활성화하지 않습니다. OAuth 앱 등록, 토큰 생성, 보안 설정 변경을 하지 않았으며 실제 OAuth/서버 게시 검증은 미완료입니다.

1. 인증 방식 비교와 결정 전 확인 사항

A. GitHub Pages + 로컬 계정: 서버 인증·인가 불가. 채택하지 않습니다.
   정적 관리자 HTML/JS는 열람 가능합니다. URL 비공개나 UI 숨김은 접근 통제가 아닙니다.
B. 기존 GitHub 계정 + 별도 동일 출처 Node HTTPS 서버: 이번 변경에 비활성 상태로 구현했습니다.
   서버가 OAuth 교환, 사용자 숫자 ID 허용 목록, 권한, 세션, 게시 요청을 검증합니다.
   GitHub Pages는 공개 회사 사이트로 유지하고, 관리자와 /api 및 /auth는 별도 서버에서 함께 제공해야 합니다.
   새로운 직원 계정 대신 기존 GitHub 계정을 사용할 수 있습니다. OAuth 앱 등록과 비밀값 설정은 아직 하지 않았습니다.
   구현된 OAuth public_repo 범위는 특정 저장소 하나로 제한되지 않습니다. 운영 도입 전 이 권한 범위를 반드시 검토해야 합니다.
C. GitHub App: 지정 저장소의 Contents 권한 등으로 더 좁게 제한할 수 있어 장기적으로 권장합니다.
   별도 앱 등록/설치·키 관리·서버 구현이 필요합니다. 이번 OAuth 구현을 GitHub App이라고 표시하지 않습니다.
D. 사내 SSO/기존 인증 서버 또는 외부 인증 서비스: 이미 계약된 서비스가 확인되면 우선 재사용할 수 있습니다.
   현재 저장소에는 이러한 연결 설정이 없었습니다. 인증만 연결해도 GitHub 쓰기 권한과 게시 서버는 별도로 필요합니다.

비용: 이번 작업에서 결제·서비스 가입·유료 리소스 생성을 하지 않았습니다.
기존 서버를 재사용할 수 있는지는 확인되지 않았습니다. HTTPS 서버, 영속 디스크, 로그 보관 비용은 공급자와 용량에 따라 달라 견적이 필요합니다.
새 유료 서비스/계정이 필요한 선택지는 비용과 이유를 확인받기 전 활성화하지 않습니다.

2. 서버 실행과 활성화 조건 (설정 예시 값이나 비밀값을 이 파일에 기록하지 마세요)

로컬 확인: Git 저장소 체크아웃에서 Node 24로 node server.js 실행, http://127.0.0.1:4173/admin/ 접속.
테스트: node --test tests/admin.test.cjs
서버는 기본적으로 127.0.0.1에만 바인딩하며 인증/게시는 비활성화됩니다.
배포 ZIP에는 .git이 없습니다. ZIP만 풀어 서버를 실행하지 말고 기준 커밋의 정상 Git 체크아웃에 변경 파일을 적용하세요.

운영 서버에 필요한 환경 변수:
ADMIN_ORIGIN: 관리자의 정확한 HTTPS 출처. 외부 임의 URL을 프런트에서 입력받지 않습니다.
GITHUB_CLIENT_ID / GITHUB_CLIENT_SECRET: 사용자가 승인한 OAuth 앱의 서버 전용 설정.
CMS_GITHUB_USER_ROLES: 불변 GitHub 숫자 사용자 ID를 editor 또는 super_admin으로 연결하는 JSON 허용 목록.
CMS_STATE_DIRECTORY: 소스 체크아웃 바깥의 영속 디렉터리. 로그인 시도 횟수와 감사 메타데이터 저장용.
CMS_BRANCH: 게시 대상 브랜치. 기본 main.
CMS_PUBLISH_ENABLED: 기본 비활성. 사용자가 최종 승인한 후에만 true.
HOST / PORT: 필요 시 기존 HTTPS 프록시 뒤에 연결하는 용도로 설정. 서비스 설정 변경은 별도 승인 대상.
OAuth callback: ADMIN_ORIGIN/auth/callback

클라이언트는 /auth, /api를 동일 출처로만 호출합니다. Pages에서 외부 서버에 교차 출처 토큰을 보내지 않습니다.
TLS 종단 프록시는 지정한 출처와 경로를 그대로 전달해야 합니다. Secure / HttpOnly / SameSite=Lax / __Host- 쿠키를 사용합니다.
POST는 Origin 및 세션별 CSRF 값을 검사합니다. 브라우저가 보내는 사용자/role은 권한 근거로 사용하지 않습니다.
editor는 로컬 초안 편집만 가능하며 super_admin도 GitHub 저장소 쓰기 권한을 별도로 검사합니다.
로그인 시도 5회/15분 제한은 서버 시간과 영속 파일 기준입니다. GitHub 비밀번호 검증은 GitHub가 수행합니다.
세션은 서버 시간으로 30분 만료, 최대 8시간입니다. 세션 연장은 서버 요청이 성공해야 합니다.
세션/토큰은 메모리에만 보관하므로 재시작 시 재로그인이 필요합니다. 비밀값은 응답/파일/로그에 저장하지 않습니다.
브라우저의 작업 타이머와 서버 세션은 다릅니다. 게시 직전에 서버 세션을 다시 확인합니다.

운영 제약: 한 프로세스/한 인스턴스 전용입니다. 다중 프로세스 또는 자동 확장은 공유 세션·원자적 공유 제한 저장소로 전환한 뒤에만 허용하세요.
프록시 뒤에서는 모든 요청이 같은 IP로 보일 수 있어 직원 여러 명의 OAuth 시도가 함께 제한될 수 있습니다.
검증되지 않은 X-Forwarded-For를 신뢰하지 않습니다. 프록시별 신뢰 경계는 운영 환경에서 별도로 검증해야 합니다.
상태 디렉터리는 백업·접근 통제·로그 순환/보존 정책이 필요합니다. 파일에 토큰은 없지만 제한 기록에는 IP가 포함됩니다.
이 서버에 제공되는 정적 소스는 기준 커밋과 정합성이 있어야 합니다. 다른 게시로 원격이 앞서면 충돌로 중단하고 체크아웃/초안을 검토해야 합니다.

3. 저장·미리보기·실제 게시

임시저장: 이 출처/브라우저의 muggo-cms-draft에 콘텐츠 저장. URL로 공유되지 않습니다.
미리보기: cms_preview=1에서만 로컬 초안을 적용. 일반 공개 화면은 저장소 데이터만 표시합니다.
기존 muggo-cms-published는 삭제하지 않지만 일반 공개 화면의 실제 게시처럼 적용하지 않습니다.
실제 게시: 서버 인증 후 네 데이터 파일을 한 Git tree/commit으로 생성하고 force=false로 브랜치를 한 번 갱신합니다.
기준 커밋 불일치 또는 경합은 409로 중단합니다. tree/commit 객체만 생성되고 브랜치가 바뀌지 않는 실패는 공개 반영이 아닙니다.
반영 후 브랜치 SHA와 tree의 파일 SHA들을 읽어 검증해야 원격 커밋 확인을 표시합니다.
네트워크가 갱신 직후 끊기면 커밋이 존재할 수 있습니다. 성공으로 추정하거나 자동 재시도하지 말고 원격 커밋/이력을 확인하세요.
GitHub 커밋 확인은 Pages 배포 성공과 다릅니다. 배포 작업과 공개 화면의 데이터가 확인되기 전에는 배포 완료라고 하지 않습니다.
index.html을 덮어쓰는 자동 버전 치환은 제거했습니다. 운영 배포의 캐시 정책도 실제 환경에서 검증해야 합니다.

4. 초안/계정/볼트/이력 보존과 복구

직원 각자가 기존 운영 출처의 관리자에서 백업을 다운로드해야 합니다. 새 서버나 localhost는 다른 출처이므로 기존 브라우저 저장소를 읽을 수 없습니다.
운영 변경 전에 기존 버전의 전체 JSON 백업도 내려받으세요. 기존 백업에 계정/볼트/이력이 포함되지 않았다면 다음 수동 백업 방법으로 추가 보관하세요.
사용자가 해당 운영 출처에서 직접 개발자 도구를 열어 필요한 기존 localStorage 키 값을 JSON으로 로컬 파일에 보관할 수 있습니다.
대상 키: muggo-cms-draft, muggo-cms-published, muggo-cms-accounts-v1, muggo-cms-aes-vault-v1, muggo-cms-audit-log-v1, muggo-admin-ui-lang.
이 값을 채팅·이메일·로그로 보내지 마세요. 브라우저 저장소 삭제, 사이트 데이터 초기화, 기존 계정 비밀번호 변경을 하지 마세요.
개선 버전의 전체 JSON 백업은 현재 콘텐츠, 기존 키의 원문, 자동 보존본을 포함합니다. 계정 해시와 암호화 볼트가 포함되어 안전하게 보관해야 합니다.
기존 볼트 재암호화와 로컬 계정 변경은 중단했습니다. 암호화 원문은 그대로 남습니다. 기존 계정은 새 서버 권한으로 이전되지 않습니다.
콘텐츠 JSON 복원은 data만 가져오며 계정·볼트·권한을 덮어쓰지 않습니다. 자격정보 복원을 자동으로 수행하지 않습니다.
롤백/가져오기 전에 기존 저장소와 현재 작업 데이터를 새 보존 키로 저장합니다. 저장 공간 부족이면 작업을 중단하고 다운로드 백업을 안내합니다.
보안/백업 메뉴에서 자동 보존본을 로컬 초안으로 다시 복원할 수 있습니다. 기존 이력·스냅샷을 25개로 잘라 삭제하는 처리를 제거했습니다.
전체 브라우저 상태를 수동 복원해야 하면 대상 출처의 현재 상태를 먼저 백업한 뒤 기존 키만 선별적으로 복원하세요.
백업 가져오기만으로 계정이 공유되거나 서버 권한이 부여되지 않습니다.

실제 게시 롤백은 구현하지 않았습니다. UI 버튼은 로컬 스냅샷 복원으로 표시합니다.
실제 공개 버전을 되돌릴 때는 대상 커밋을 특정하고 변경 내용을 검토한 Git revert를 별도 승인 후 수행하고 Pages 배포/공개 화면까지 검증해야 합니다.

5. 배포 승인 전 필수 확인

이번 결과를 그대로 운영 보안 완료라고 판단하지 마세요.
승인된 서버/인증 방식과 범위를 결정하고 HTTPS 스테이징에서 실제 OAuth, 쿠키, 만료, 로그아웃, IP 제한을 확인해야 합니다.
격리된 테스트 저장소에서 실제 GitHub 오류/권한/브랜치 보호/원자적 커밋을 검증해야 합니다. 운영 채용 데이터로 테스트하지 않습니다.
브라우저의 데스크톱·모바일, ID/EN/KO 공개 화면 대조, 직원 백업 복원, Pages 캐시/배포 완료 확인도 남아 있습니다.
그 증거와 최종 diff를 다시 보여주고 사용자에게 운영 배포 승인을 받아야 합니다.
